*Spec: Keep an accepted `run_agents` action alive while a remote child recovers from GitHub auth (REMOTE-2616)*

== Summary ==

Today, when one child of an accepted `run_agents` dispatch hits a GitHub-authentication blocker at launch, the parent orchestration action terminates as a failure for that child while the child pane separately recovers once the user completes OAuth. The transcript shows a misleading terminal state ("Failed to spawn agent" / "Spawned X of Y agents"), the parent sends its follow-up without the blocked child's `agent_id`, and a re-run risks duplicate children. This change makes the accepted `run_agents` action stay alive in a new nonterminal `AIActionStatus::BlockedOnUserAction` status while any child is recoverably blocked, retries each blocked child exactly once per process-wide GitHub OAuth completion through a retained pending start-agent request, and surfaces one grouped remediation card. The change is client-only.

== Product behavior ==

1. When the user accepts a `run_agents` action and one or more remote children report a recoverable GitHub-auth blocker at launch, the parent action enters `AIActionStatus::BlockedOnUserAction` and stays in `running_actions`. The action is not finished, not requeued, and not re-executed.
2. While the parent action is `BlockedOnUserAction`, the parent conversation status stays `InProgress`. The conversation does not enter `ConversationStatus::Blocked`, the input is not hidden, focus is not captured, and no approval confirmation UI is shown for the parent action.
3. The grouped remediation card replaces the "Spawning N agents…" card. It shows the existing post-confirmation cloud-agent GitHub-auth presentation (title "GitHub Authentication Required", the server-provided public blocker message, one "Authenticate with GitHub" button that opens the normalized auth URL). It shows grouped counts (launched children and blocked children) and renders one row per distinct permanent child failure. It renders no run-wide parameter controls: no model, harness, execution-mode, environment, runner, or auth-secret pickers.
4. When the user completes GitHub OAuth, a single process-wide completion event reaches every eligible blocked child of every `run_agents` action. Each blocked child is re-dispatched exactly once per completion, using its retained request. Children that are launched, permanently failed, cancelled, or already re-dispatching do not re-dispatch.
5. A blocked child's pending start-agent request survives the blocker. It closes only on: successful start (`Started { agent_id }`), permanent failure, the per-attempt timeout, or cancellation.
6. When no blocker remains and the re-dispatched children are launching again, the parent action returns to `AIActionStatus::RunningAsync` and the card returns to "Spawning N agents…". A child that is blocked again after a retry (for example, the wrong account authorizes) re-enters `BlockedOnUserAction`; the next completion retries it again. Every retry is gated on a new human OAuth completion, so there is no automated retry loop.
7. The 30-second spawn timeout applies per automated attempt. It does not run while a child is blocked awaiting human auth. Each retry re-arms a fresh 30-second timer. A timeout is a permanent failure for that child.
8. In a partial batch, children that already launched keep running across the blocker and the recovery. The final `RunAgentsResult::Launched` lists one outcome per input child in input order, with children that started after recovery reported as `Launched`.
9. When the user cancels the parent action while it is `BlockedOnUserAction`: all unresolved retained child requests are cleared, later updates for those requests are ignored, a server task that resolves after the cancellation (raced retry) is cancelled, and already launched sibling children keep running. The action finishes as cancelled.
10. Permanent child failures never produce a CTA. They appear as rows in the grouped card and as `Failed { error }` outcomes in the final result.
11. Local (`RunAgentsExecutionMode::Local`) children never produce a GitHub-auth blocker; the recovery path exists for remote children only, and the status shape is shared across all action types (only `RunAgents` produces it today).
12. On session restore or in view-only (shared-session viewer) surfaces, a `BlockedOnUserAction` state never persists: restored blocks render their recorded terminal result as today, and viewers see the grouped card without an interactive CTA button.

== Technical design ==

*Current state (this checkout, `aa9f3a43`):*

- `AIActionStatus` (`app/src/ai/blocklist/action_model.rs:74-93`) has `Preprocessing | Queued | Blocked | RunningAsync | Finished(Arc<AIAgentActionResult>)`. `Blocked` means "front of the pending queue, awaiting user approval, not started" (`get_action_status`, `action_model.rs:616-648`); it is only ever derived for a pending action when the conversation has no running actions.
- `RunAgentsExecutor` (`app/src/ai/blocklist/action_model/execute/run_agents.rs`) fans out per child through `StartAgentExecutor::dispatch` and aggregates. The aggregation loop (`run_agents.rs:293-336`) awaits each child's `Receiver<StartAgentOutcome>` sequentially, with a fixed `SPAWN_TIMEOUT = 30s` per slot (`run_agents.rs:47`). `StartAgentOutcome` is `Started { agent_id } | Error(String)` (`start_agent.rs:12-19`) over a `bounded(1)` channel: one update per child, then the channel closes.
- The GitHub-auth blocker for a remote child is detected in the child pane's spawn stream: `classify_cloud_agent_startup_error` (`app/src/ai/orchestration/remote_child.rs:325-333`) maps a `ClientError` carrying `auth_url` to `CloudAgentStartupIssue::Blocked(CloudAgentStartupBlocker::GitHubAuthRequired { message, auth_url })` (blocker type at `remote_child.rs:135-152`; the URL is normalized by `cloud_setup_auth_url_with_next`, `app/src/ai/ambient_agents/github_auth_url.rs:53`). The child's `AmbientAgentViewModel` enters `Status::NeedsGithubAuth { progress, error_message, auth_url }` (`app/src/terminal/view/ambient_agent/model.rs:111`), and `TerminalView`'s handler sets the child conversation to `ConversationStatus::Blocked { blocked_action: CHILD_AGENT_GITHUB_AUTH_REQUIRED_BLOCKED_ACTION }` (`app/src/terminal/view/ambient_agent/view_impl.rs:300-311`; constant at `view_impl.rs:41-42`).
- The parent path learns of the blocker only through the lossy conversation status: `StartAgentExecutor::handle_history_event` on `UpdatedConversationStatus` calls `start_agent_error_message_for_status` (`app/src/ai/blocklist/action_model/execute/start_agent.rs:297-330`), which maps child `ConversationStatus::Blocked { blocked_action }` to `Some(error)` and completes the pending request as `StartAgentOutcome::Error(blocked_action)` (`complete_pending_as_error`, `start_agent.rs:130-154`). `should_cleanup_failed_child_launch` (`start_agent.rs:286-295`) keeps the blocked child's chip but the request is gone.
- The child pane independently retains its own request and re-spawns on OAuth completion (`handle_github_auth_completed`, `ambient_agent/model.rs:1438-1448`, via the process-wide `GitHubAuthNotifier::AuthCompleted` singleton, `app/src/ai/ambient_agents/github_auth_notifier.rs`). There is no generation or attempt accounting: a duplicate or late `AuthCompleted` can double-spawn, and a callback that races the blocker is lost.
- Child launch plumbing: `StartAgentExecutorEvent::CreateAgent` (`start_agent.rs:336-344`) → `TerminalView` handler (`app/src/terminal/view.rs:7640-7660`) → `Event::StartAgentConversation` → `dispatch_start_agent_conversation` (`app/src/pane_group/pane/terminal_pane.rs:1489-1573`) → `launch_remote_child` (`terminal_pane.rs:1876-1969`), which records the child conversation id back onto the pending request and calls `AmbientAgentViewModel::spawn_agent_with_request`.
- GUI card (`app/src/ai/blocklist/inline_action/run_agents_card_view.rs`) renders `Blocked` as the confirmation card (pickers included), `RunningAsync`/spawning as "Spawning N agents…", `Finished` as the terminal status card (`format_terminal_state`, `run_agents_card_view.rs:1604-1656`). TUI: `tool_call_display_state` (`crates/warp_tui/src/tool_call_labels.rs:122-157`) collapses statuses to `ToolCallDisplayState`, and `Blocked` appends " (awaiting approval)" (`tool_call_labels.rs:188-189`); the TUI orchestration block renders interactively only for `AIActionStatus::Blocked` (`crates/warp_tui/src/orchestration_block/render.rs:234-241`); input blocking derives from `Blocked` (`crates/warp_tui/src/agent_block.rs:965-1005`); the OSC publisher emits `permission_request` from `ActionBlockedOnUserConfirmation` with a `Blocked` label (`crates/warp_tui/src/cli_agent_osc_event_publisher.rs:99-137`).

*Proposed changes:*

1. **New status variant.** Add `AIActionStatus::BlockedOnUserAction` (unit variant, nonterminal) in `app/src/ai/blocklist/action_model.rs`. Add `is_blocked_on_user_action()`; keep `is_blocked()` approval-only. `get_action_status` returns `BlockedOnUserAction` for an action in `running_actions` whose executor reports one or more recoverably blocked children. `RunningAsync` and `BlockedOnUserAction` are both "in `running_actions`" statuses; they differ in whether a user-action blocker is projected.
2. **Typed start-agent update stream.** Extend the per-child channel from a one-shot `StartAgentOutcome` to a multi-update stream `StartAgentUpdate` with `BlockedOnUserAction { blocker: CloudAgentStartupBlocker }`, `Started { agent_id }`, and `FailedPermanently { error }` (exported through `tui_export.rs` where the executor types already cross the crate boundary). The blocker payload is the structured, already-normalized `CloudAgentStartupBlocker::GitHubAuthRequired { message, auth_url }`; the parent never re-derives it from strings. `StartAgentExecutor` gains `report_blocked(child_conversation_id, blocker)`, called from the child-pane wiring where `AmbientAgentViewModelEvent::NeedsGithubAuth` is handled, and forwards the update onto the retained request's channel. `PendingStartAgent` survives the blocker: it is removed only on start, permanent failure, executor-side timeout, or cancellation. `start_agent_error_message_for_status` drops its `Blocked` arm for the start path — a child's `ConversationStatus::Blocked` no longer closes a pending request; `Error` and `Cancelled` still do. `should_cleanup_failed_child_launch` is unchanged.
3. **Per-child state machine in `RunAgentsExecutor`.** Each child slot holds `Launching { attempt: u32, dispatched_generation: u64 } | BlockedOnAuth { attempt, blocker, seen_generation: u64 } | Failed { error } | Started { agent_id } | Cancelled`. Transitions:
   - `Launching` —update `Started`→ `Started` (closes the pending request).
   - `Launching` —update `FailedPermanently`→ `Failed` (closes the pending request).
   - `Launching` —timeout→ `Failed` with the existing timeout error text (timer armed per attempt only).
   - `Launching` —update `BlockedOnUserAction`→ `BlockedOnAuth`: record `seen_generation` = the recovery coordinator's latest completed-auth generation, keep the pending request open, pause the attempt timer. If a completion was already recorded after this attempt began dispatching (`latest > dispatched_generation`), retry immediately (rule 6's callback-before-blocker case), exactly once.
   - `BlockedOnAuth` —`AuthCompleted` with generation `> seen_generation`→ `Launching { attempt + 1 }`: re-dispatch the retained request through the same `StartAgentExecutor::dispatch` path and arm a fresh 30-second timer. The state transition itself is the exactly-once guard: the first callback per child per generation moves the child out of `BlockedOnAuth`, so duplicate notifier emissions are no-ops.
   - any —parent cancellation→ `Cancelled`: clear the retained pending request, ignore later updates, and cancel a raced server task through the existing TaskSpawned-after-cancel pattern (`ambient_agent/model.rs:1177-1184`).
4. **Recovery coordination.** Subscribers of the `GitHubAuthNotifier` singleton keep a process-wide monotonically increasing completion-generation counter (increment on every `AuthCompleted`). One subscription per `RunAgentsExecutor`, not per child: a single completion fans out to every child in `BlockedOnAuth` whose `seen_generation` is older. Retried children keep their original request fields (prompt, execution mode, config) held by the pending start-agent request; nothing is re-read from the plan or re-resolved.
5. **Concurrent aggregation, ordered result.** Replace the sequential per-slot await (`run_agents.rs:293-336`) with concurrent processing of all children's update streams (`join_all` over per-child update processors, each owning its timeout and retry loop). Each processor records its outcome at its input index. The final `RunAgentsResult::Launched` is composed after all children reach a terminal state, in input order, so transcript ordering is unchanged.
6. **Executor-owned snapshot, events invalidate views.** `RunAgentsExecutor` exposes a progress snapshot per action: `{ total, launched, blocked_on_auth: Option<CloudAgentStartupBlocker>, failed: Vec<(name, error)> }`. Extend `RunAgentsExecutorEvent` with `ProgressChanged { action_id }` (and `BlockedOnUserAction { action_id }` or fold both into `ProgressChanged`). Views subscribe, store nothing, and re-render by reading the snapshot: the GUI card (`run_agents_card_view.rs`) and the TUI block (`orchestration_block.rs`) replace their `spawning: Option<RunAgentsSpawningSnapshot>` caching with snapshot reads.
7. **Grouped remediation card (GUI and TUI).** In `BlockedOnUserAction`, both frontends render one card: the `CloudAgentStartupPresentation::github_auth(auth_url, CloudAgentStartupAuthFlow::RetryRetainedRequest)` content (`remote_child.rs:206-222`) reused from the existing cloud-mode auth screen (`app/src/terminal/view/ambient_agent/loading_screen.rs:300-396`), plus a counts line ("Spawned {launched} · Waiting on GitHub auth: {blocked}") and one row per distinct permanent failure (deduplicated by error text). No run-wide parameter rendering: the confirmation card's pickers and mode toggle are not shown. The button opens the normalized `auth_url`. The child panes keep their existing per-child auth footer and presentation.
8. **Consumer audit — runtime remediation is not approval.** Every consumer that must distinguish the new variant, and how:
   - `is_blocked()` (`action_model.rs:105-107`) stays approval-only; add `is_blocked_on_user_action()`.
   - GUI active-blocker derivation `app/src/ai/blocklist/block/model/helper.rs:156` (and `output.rs` `is_blocked()` call sites at 1352, 2015, 2129, 2311, 2364, 2745, 2862, 2948, 3254): unchanged — `BlockedOnUserAction` does not become the front-of-queue confirmation action.
   - GUI card views keyed on `AIActionStatus::Blocked` (`run_agents_card_view.rs:797, 1269, 1278`; `requested_command.rs:1200-1415`; `code_diff_view.rs:618`; `ask_user_question_view.rs:372-1157`; `search_codebase.rs:459-487`; `block.rs:3460, 4075, 4733-4827`; `output.rs:1488-1558, 2429-2438, 3836-3840`): exhaustive matches get a `BlockedOnUserAction` arm that renders as nonterminal-and-not-approving (running-like) — only `RunAgents` can produce it, and the run_agents card renders its own CTA.
   - TUI `tool_call_display_state` (`tool_call_labels.rs:122-157`): map `BlockedOnUserAction` to a new `ToolCallDisplayState::AwaitingUserAction` with the running glyph ("●", attention style) and no "(awaiting approval)" suffix; the RunAgents label is "Waiting for GitHub authentication…". `tool_call_labels_tests.rs` covers the mapping.
   - TUI input focus (`agent_block.rs:965-1005` `active_blocking_input_source`) and `orchestration_block/render.rs:234-241`: do not match `BlockedOnUserAction` — no input capture, no interactive confirmation card.
   - OSC permission events (`cli_agent_osc_event_publisher.rs:99-137`): `BlockedOnUserAction` produces no `permission_request` notification. It is not routed through `BlocklistAIActionEvent::ActionBlockedOnUserConfirmation` at all; the card subscribes to `RunAgentsExecutorEvent::ProgressChanged` instead.
   - Cancellation routing (`cancel_action_with_id`, `action_model.rs:1061-1090`; `cancel_running_async_action`, `execute.rs:854`; `cancel_all_pending_actions`, `action_model.rs:1124-1169`): `RunAgentsExecutor::cancel_execution` extends beyond the `Publishing` phase to cancel the recovery state per rule 9. Launched siblings keep running; the parent action result is `RunAgentsResult::Cancelled` through the existing path.
9. **Child conversation status on retry.** When the executor re-dispatches a blocked child, the child conversation returns to `ConversationStatus::InProgress` (mirroring the `FollowupDispatched` status update at `view_impl.rs:193-203`), so the child chip does not stay yellow while its spawn is in flight.

*Data flow (recovery):* server spawn error (`ClientError.auth_url`) → child-pane `AmbientAgentViewModel` classifies to `CloudAgentStartupBlocker::GitHubAuthRequired` → child conversation `ConversationStatus::Blocked` (presentation, unchanged) **and** `StartAgentExecutor::report_blocked(child_id, blocker)` → update stream to `RunAgentsExecutor` → child slot `BlockedOnAuth`, parent status `BlockedOnUserAction`, card snapshot updated → user completes OAuth → `GitHubAuthNotifier::AuthCompleted` → generation bump → executor re-dispatches retained request (`attempt + 1`) → child spawns → `Started { agent_id }` closes the pending request → all children terminal → `RunAgentsResult::Launched` in input order → parent action `Finished`, follow-up proceeds.

== Decisions ==

1. **Status shape: new variant vs. projecting `Blocked` vs. requeueing.**
   - *Chosen: add `AIActionStatus::BlockedOnUserAction`.* The action stays in `running_actions`; the type system carries the distinction. Exhaustive matches force every consumer to decide explicitly, which is exactly the audit requirement ("must explicitly distinguish runtime remediation from approval"). The parent's action queue, phase bookkeeping, and conversation status logic are untouched.
   - *Rejected: project the existing `Blocked` from a running action.* `Blocked` is defined as "front of the pending queue, not started" and every approval surface keys off it: input hiding, `active_blocking_input_source` focus capture (`agent_block.rs:965-1005`), the OSC `permission_request` notification, `ConversationStatus::Blocked`, and `helper.rs:156`'s active-blocker derivation. Deriving it for a running action would demand approval focus for a remediation CTA, flip the parent conversation to `Blocked`, and require special cases in each consumer — worse than a new variant, and it still loses the information that the action already started.
   - *Rejected: move the action back to the pending queue.* Requeueing re-drains `try_to_execute_available_actions`, which re-enters execution and would double-dispatch children (the duplicate-name guard would then deny the legitimate retry). It also discards the running-children bookkeeping and flips the parent conversation status to `Blocked`. Root cause of the bug is that the parent treats a recoverable blocker as terminal — moving the action backwards in the queue does not correct that and adds re-execution hazards.
2. **Retry ownership: the parent's executor, not the child pane.** The child pane's own `handle_github_auth_completed` re-spawn stays for standalone cloud panes, but for a child with a parent-owned pending start-agent request, the `RunAgentsExecutor`/`StartAgentExecutor` path owns the retry and the child's self-retry is suppressed. One writer per retained request keeps "retry exactly once" enforceable, and only the executor has the attempt/generation state needed to arbitrate the timeout, duplicate-callback, and cancellation races. The child keeps presentation-only state (auth footer, status).
3. **One grouped CTA, not per-child cards.** Per-child auth cards in the parent transcript would duplicate the same remediation N times and steal interaction focus per card. One card per action with grouped counts matches the grouped pill bar and keeps a single button. Individual rows appear only where the user can act on the difference: distinct permanent failures.
4. **Structured blocker through the update stream, not the conversation status.** The existing path serializes the blocker to `blocked_action: String` and the parent re-parses it. The typed payload (`message`, normalized `auth_url`) already exists at the detection site (`CloudAgentStartupBlocker`); carrying it through a typed update avoids a stringly-typed round trip and keeps URL normalization in one place (`cloud_setup_auth_url_with_next`).
5. **Timeout per attempt, not cumulative.** The 30-second budget exists to catch "harness binary not installed" class failures, not to bound human OAuth. Pausing during the human wait and re-arming per attempt keeps that purpose intact; a cumulative budget would fail recovered children that merely took a while to authenticate.

== Assumptions ==

- Assumption: the server rejects the child spawn with a `ClientError` carrying `auth_url` before any server task exists, so a retry re-calls spawn on the same child conversation and no orphan task needs cleanup on the retry path itself. (Matches `classify_cloud_agent_startup_error`'s contract in this checkout.)
- Assumption: `run_agents` children auto-execute, so a child's `ConversationStatus::Blocked` in the orchestration flow is always the GitHub-auth blocker today; dropping the `Blocked` arm from `start_agent_error_message_for_status` therefore does not strand other block types. If a future child-block type appears, it must join the typed update stream rather than the lossy status mapping.
- Assumption: the OAuth completion generation counter lives process-wide (per app session) and does not need to survive restarts; a restart mid-block lands in the restore path (rule 12).

== Out of scope ==

- Server/proto changes: `RunAgentsResult` and its wire form are unchanged; the recovery happens entirely client-side before the terminal result is produced.
- New telemetry: `RunAgentsCompleted` still fires once per action at the terminal result. Recovery-rate instrumentation is deferred until there is a signal requirement.
- Standalone (non-orchestration) cloud-pane auth recovery: its existing retained-request retry is unchanged.
- Auth blockers other than GitHub (capacity, out-of-credits, server overload remain permanent `Failed` outcomes).
- Follow-up (`send_message_to_agent`) auth flows and nested multi-level children's own `run_agents` calls beyond what the shared status machinery gives them for free.

== Validation criteria ==

1. **Status projection and partial batches** — unit tests in `action_model_tests.rs` / `run_agents_tests.rs`: a batch of 3 children where one reports `BlockedOnUserAction` and one reports `Started` before the third finishes resolves the parent action as `BlockedOnUserAction` while `running_actions` still contains it, and `get_pending_action` does not return it. Verifies behaviors 1, 2.
2. **Recovery to `RunningAsync`** — after a completion generation bump re-dispatches the blocked child, the action returns to `RunningAsync` and only reaches `Finished(Launched { agents })` when every child is terminal, with input-order outcomes and recovered children as `Launched`. Verifies behaviors 4, 6, 8.
3. **Exactly-once retry** — with the notifier emitting two `AuthCompleted` events per completion and a second blocker after the first retry, tests assert: one re-dispatch per child per generation; no re-dispatch for `Started`/`Failed`/`Cancelled` children; callback-before-blocker retries immediately. Verifies behaviors 4, 6.
4. **Timeout semantics** — a child blocked on auth for longer than 30 seconds is not failed while blocked; an automated attempt that exceeds 30 seconds fails with the existing timeout text; a retried attempt re-arms a fresh timer. Verifies behavior 7.
5. **Pending-request lifecycle** — the pending start-agent request survives the blocker (no `complete_pending_as_error` from a child `ConversationStatus::Blocked`) and closes on start, permanent failure, timeout, and cancellation. Verifies behavior 5 and the `start_agent_error_message_for_status` change.
6. **Cancellation** — cancelling the parent action while blocked clears retained requests, ignores a late `BlockedOnUserAction`/`Started` update, cancels the raced server task, keeps launched siblings running, and finishes the action as cancelled. Verifies behavior 9.
7. **Grouped card** — GUI test (`run_agents_card_view_tests.rs`) and TUI test (`orchestration_block_tests.rs`): the `BlockedOnUserAction` render shows the auth presentation, grouped launched/blocked counts, one row per distinct permanent failure, and no picker or mode-toggle elements; the "Spawning…" card returns when the blocker clears. Verifies behaviors 3, 4.
8. **No approval semantics leak** — tests assert: no `ActionBlockedOnUserConfirmation` emission for the parent action, parent `ConversationStatus` stays `InProgress`, TUI `active_blocking_input_source` is `None`, `tool_call_display_state` renders the new state without the "(awaiting approval)" suffix, and the OSC publisher sends no `permission_request`. Verifies behavior 2 and the consumer audit.
9. **Existing suites stay green** — `run_agents_tests.rs`, `start_agent` tests, `tool_call_labels_tests.rs`, `orchestration_block_tests.rs`, and the action-model tests pass unchanged except where extended above; `./script/presubmit` at the repo root is green. Verifies behaviors 11, 12 and no regression in the un-audited surfaces.

== Approval gate ==

Reviewer approval is requested on two decisions before implementation starts:
1. **Status shape:** the new nonterminal `AIActionStatus::BlockedOnUserAction` unit variant, projected from a running `run_agents` action, with executor-held structured data (Decision 1).
2. **Partial-batch semantics:** `BlockedOnUserAction` projects whenever any child is recoverably blocked, regardless of launched/failed/launching/retrying siblings, with the return to `RunningAsync` governed by "no blocker remains and automated work continues" (behaviors 1, 2, 6, 8).
